When the model calls a tool, the reply gets a `tool_call` segment and the bubble draws it as a
quiet row: the tool's name and its status. Opening the row shows the input the model chose and
the result your handler returned. The row is drawn for you; a tool registered with
`aparteGlobalConfig.registerTool()` produces it during a turn without any code of yours.

## Variants

### Every status

<Variant id="tool-statuses" />

A call is `pending` while your handler runs, `awaiting-approval` when the tool is marked
`needsApproval` and a person has to decide (see [Tools and approval](/guides/tools/)), then
`resolved`, `rejected`, `aborted` or `failed`. Only the first two are still open. A refused or stopped call also says why, in a note after
the state word: `You said: “…”` when the person wrote something instead of choosing, `Refused by
policy`, `Not run: an earlier call was refused`, `Timed out`, `Not available here`, `No one could
approve it` or `Turn limit reached`. A plain Stop has no note. The segment keeps `refusal`
(`{ by, instruction? }`) and `abortCause`, and its `result` stays the sentence the model read;
the full table is in [Tools and approval](/guides/tools/#what-the-row-shows).

### A summary of what it ran on

<Variant id="tool-summary" />

`registerToolSummary(match, summary)` adds one line after the tool's name, so `read_file` reads
`read_file docs/release.md` without opening the row. It returns plain text; the row, its states
and its disclosure stay the library's. `registerToolInputFormatter(match, formatter)` rewrites the
arguments behind the disclosure, and the approval panel shows the same text. `match` is a tool
name, a `RegExp` or `'*'` (every tool nothing more specific describes); both write one field of the
tool's display, below.

### A name and an icon of its own

<Variant id="tool-display" />

`registerToolDisplay(match, display)` gathers everything about how a tool's calls look. `label`
replaces the identifier `web_search` with words, drawn in the chat's own font, not the code font;
`icon` is an icon-provider key (an unknown one falls back to `tool`; `search` and `globe` come from
`@aparte/core/icons`). The identifier stays on the row as `data-tool-name`. Core never turns an
identifier into words on its own: the label is yours to write.

### Hidden calls

<Variant id="tool-hidden" />

`hidden: true` draws nothing for the tool's calls. They stay in the message, in storage and in
the history the model reads, and an approval they need is still asked.

### Rows opened by default

<Variant id="tool-open" />

A row is closed unless something opens it: `open: true` on a tool's display opens its rows, and
`setSegmentDefaults('tool_call', { collapsed: false })` opens every row. A segment's own
`collapsed` wins over both.

### Your own rendering

<Variant id="tool-renderer" />

`registerToolRenderer(match, renderer)` replaces the row for one tool, for every tool a pattern
names, or, with `'*'`, for every tool without a renderer of its own. An empty render hides the
call (it stays in the history). Return an element rather
than an HTML string: the input and the result come from the model and your tool, so a string
would have to escape every value it interpolates. Add an `update()` to patch the element when
the result lands, instead of rebuilding it.

## Usage

```ts
import { aparteGlobalConfig } from '@aparte/core';

aparteGlobalConfig.registerTool(
  {
    name: 'get_weather',
    description: 'Current weather for a city.',
    inputSchema: { type: 'object', properties: { city: { type: 'string' } }, required: ['city'] },
  },
  async (call) => ({ toolCallId: call.id, content: `Cloudy, 14 °C in ${call.input.city}.` }),
);
```

The client offers the tool to the model, runs the handler when it is called and draws the row
for each call. Building a segment by hand, as these demos do, is for a reply your own code
assembles.

To choose labels, icons and what is shown, read [Showing tool calls to a person, or to a
developer](/guides/tool-display/): it covers how a display is matched, hiding every call, and
opening the rows.

## Accessibility

- When there is an input or a result to show, the row is a native `<details>`: its summary opens
  with Enter or Space and announces whether it is expanded. With nothing behind it, it is a
  plain row and takes no tab stop.
- The status is written in words (locale keys such as `toolRunning`, `toolCompleted`,
  `toolFailed`), not only shown as a colour or an icon.
- Input and Output are focusable regions named by their label, so a long part that scrolls past
  `--aparte-tool-part-max-height` (300px) can be read with the keyboard; each has a copy button.
