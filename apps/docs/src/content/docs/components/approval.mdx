Some tools should not run without a yes: deleting a file, sending an email, running a command.
Mark such a tool `needsApproval` and the turn stops before its handler runs. The tool's row
in the transcript says it is waiting, and the question is asked where the person is already
looking, at the composer: which tool, with which arguments, approve or reject.

The question names the call the way its row does: the tool's label (its identifier when it has
none), then what its summary says it targets, so a tool labelled "Delete a file" can ask "Run
Delete a file a.ts?" ("Allow …?" by default). The arguments block under it is unchanged. The question is the built-in channel's, `AparteClient`'s; an app with its own loop writes its own. The locale key `approvalAsk` is
the lever for the wording; an app that gives its tools action labels would write `'Allow {tool}?'`.

The person can also type an answer instead of clicking: "no, archive it instead". That
refuses the call, and the words reach the model as the tool's result, so the next step can
follow them. The row quotes them back to the person (`You said: “no, archive it instead”`);
a call refused by a [policy](/guides/tools/#decide-in-code) says `Refused by policy`
instead. When a paused [server run](/guides/server-loop/) asks about several calls at once, the
ones after a refusal are not run, and say `Not run: an earlier call was refused`.

The chevron in the panel's corner puts it aside, to read the transcript behind it, and leaves a
one-line bar that brings it back; the call keeps waiting meanwhile.

The options come with the request, so an app that can remember a grant offers a third one,
and says what it reaches. Offer "always" only where your app keeps it.

## Usage

With `AparteClient`, marking the tool is all it takes:

```ts
import { aparteGlobalConfig } from '@aparte/core';

aparteGlobalConfig.registerTool(
  {
    name: 'delete_file',
    description: 'Delete a file from the workspace.',
    inputSchema: { type: 'object', properties: { path: { type: 'string' } }, required: ['path'] },
    needsApproval: true,
  },
  async (call) => ({ toolCallId: call.id, content: `Deleted ${String(call.input['path'])}.` }),
);
```

To ask on your own terms, call `requestUserInput()` with `kind: 'approval'`. It resolves with
the chosen option's `value`, or with the typed `instruction`:

```ts
import { requestUserInput } from '@aparte/core';
import type { AparteApprovalAnswer } from '@aparte/core';

const result = await requestUserInput({
  kind: 'approval',
  message: 'Run run_command?',
  details: 'git status',
  options: [
    { value: 'once', label: 'Allow once' },
    { value: 'always', label: 'Always allow', description: 'git status, in this workspace' },
    { value: 'reject', label: 'Reject', tone: 'deny' },
  ],
});
if (result.action === 'accept') {
  const { option, instruction } = result.content as AparteApprovalAnswer;
}
```

`allowOther: false` leaves the instruction field out, for a decision that has to be one of the
options, as it leaves a question's "Other…" out; the corner still declines, since an unanswered approval is never a yes.

An `AparteApprovalOption` has a `value`, a `label`, an optional `description` (what choosing it
commits to) and a `tone`, `affirm` or `deny`. A label can be a function, re-read when the
language changes while the question is open.

## Customize

- Which calls ask is a policy: the [approval mode](/components/approval-mode/) switch decides
  by mode (plan, ask, auto-edit, auto) from your tool names.
- `AparteClient`'s `approvalResolver` option takes the whole decision instead, for a CLI, a
  webhook or a rule written in code. On a refusal it can answer `by: 'policy'` so the row does
  not credit the refusal to a person.
- `registerToolDisplay` gives a tool a label, an icon and a summary, which the question then
  reads: [Showing tool calls](/guides/tool-display/).
- The panel is capped at `--aparte-elic-max-height`, half the window by default.

## Accessibility

- The arguments are shown as text, in a focusable group named "Arguments", never as markup:
  they are written by the model.
- The options are buttons in a group named from the `approvalOptionsLabel` key ("Your
  decision"); a decision takes one click or one key press.
- The instruction field is named by its placeholder ("Or tell it what to do instead…").
- The panel takes the focus and gives it back when it closes (to the composer when there is nothing
  to go back to). From the chat's own editor it focuses the panel itself, named by the question, so
  the next key does not pick an option. A reader writing in a field elsewhere on the page, or in
  another chat, keeps the focus, and a polite status says a question waits. Taken from nowhere, it
  does not scroll the page.
- The hide button and the bar it leaves carry `aria-expanded`, and each takes the focus from the
  other.
